## 1. 개요와 문제

**결산체크는 월말 결산 자료의 요청·제출 상태를 재무와 각 부서·팀장이 같은 주소에서 함께 보는 웹 현황판이다.** 재무가 요청을 등록하면 각 부서가 기존 채널로 자료를 제출하고 완료를 표시한다.

**선정 근거.** PPT 2장의 후보 평가에서 결산 자료 제출 확인·독촉은 빈도 4점, 시간 5점, 실수 4점으로 총 13점이다. 비품 신청(11점), 계약 만료 관리(10점)보다 우선했다. 후보 출처는 AI 인터뷰이며 실제 현업 검증 결과로 간주하지 않는다. 경비 내역 취합은 개발자 지인 확인을 거쳐 ERP로 이미 해결되는 문제로 판단해 제외했다.

**As-Is (PPT 3장, 가상 시간)**

| 단계 | 업무 | 월 소요 시간 |
| --- | --- | --- |
| 1 | 부서별 자료·기한 정리와 요청 메일 발송 | 약 1시간 |
| 2 | 회신 확인과 개인 엑셀 제출 여부 표시 | 약 2시간 |
| 3 | 미제출·누락 부서 독촉과 재요청 | 약 2시간 |
| 4 | 팀장 보고용 진행 상황 재정리 | 약 1시간 |

**근본 원인.** 요청·제출 상태가 담당자 개인 엑셀에만 있고 부서와 팀장이 함께 볼 공용 현황판이 없다. PPT에서는 ERP가 제출된 자료의 전표 처리를 담당한다고 가정한다. 회사별 ERP 기능 차이는 현업 적용 시 확인한다.

**To-Be.** 재무가 요청을 한 번 등록하고, 부서가 직접 제출 완료를 표시하며, 재무·부서·팀장이 같은 현황과 진행률을 확인한다. 요청 안내와 독촉 메시지 문구 작성은 AI 채팅으로 처리한다.

**효과 목표 (가상 수치, 검증할 가설)**

| 지표 | As-Is | To-Be |
| --- | --- | --- |
| 요청·제출 확인·독촉·보고 전체 업무 시간 | 월 약 6시간 | 월 약 1시간 목표 |
| 제출 현황 공유 대상 | 재무 담당자 1명 | 재무·각 부서·팀장 |
| 보고 준비 | 엑셀 재정리 약 1시간 | 현황판 주소 공유, 별도 엑셀 재정리 생략 |

6시간은 요청 메일 발송까지 포함한 전체 시간이다. 구현 후 등록·안내·자료 검증·독촉·보고에 실제 걸린 시간을 합산해 목표를 검증한다. 주소 공유 시간을 0분으로 단정하지 않는다. 오늘은 시간 절감 실적 대신 아래 기능 통과 여부를 확인한다.

**중간 점검:** 입력 → 공용 저장 → 다른 PC에서 조회 + 인터넷 주소 1개(F1·F2). F3까지 구현하면 부서가 직접 상태를 공유할 수 있다. 최종 완료는 README의 완료 조건에 따라 F1~F5와 배포 주소 검증을 모두 통과해야 한다.

## 2. 사용자와 사용 흐름

| 사용자 | 하는 일 | 얻는 것 |
| --- | --- | --- |
| 재무 담당자 | 요청 등록, 미제출·지연 확인 | 제출 상태를 한곳에서 확인 |
| 부서 담당자 | 우리 부서 자료·기한 확인, 제출 완료·취소 | 제출할 자료와 기한을 직접 확인 |
| 팀장 | 진행률·지연 확인 | 별도 보고 없이 현황 확인 |

모두 같은 주소와 화면을 사용한다. 사용자 구분은 업무상 역할이며 로그인·권한 제한을 뜻하지 않는다.

**4단계 흐름:** 요청 등록 → 부서가 자료·기한 확인 → 메일·ERP로 제출 후 완료 표시 → 재무·팀장이 현황 확인.

**대표 시나리오.** 재무가 2026-09 결산 요청 16건을 등록하고 주소를 공유한다. 구매팀은 미지급 내역을 ERP에 제출한 뒤 완료를 표시한다. 제출 완료 10건이면 팀장은 진행률 62%와 지연 2건을 확인한다. 재무는 지연 부서에 독촉하고 누락 자료는 기존 방식으로 확인·재요청한다.

## 3. 범위와 기본값

**포함:** 요청 등록·공용 저장, 현황 목록, 제출 완료·취소, 기한 강조, 결산월·부서 필터와 진행률, 공용 인터넷 주소.

**제외:** 파일 첨부, 로그인·부서별 권한, 자동 알림, ERP 연동, 앱 내 안내문·독촉 문구 생성, 변경 이력 보관.

- 요청 1건은 자료 1개 × 부서 1곳이다. 여러 부서가 제출하면 부서별 요청을 등록한다.
- 상태는 `미제출` / `제출 완료`다. 완료는 부서의 직접 신고이며 재무의 검증 완료를 의미하지 않는다.
- 부서 기본 목록: 영업팀, 생산팀, 구매팀, 인사팀, 총무팀, 연구소. 데이터 담당이 변경하면 폼·필터·샘플 데이터에 동일하게 적용한다.
- 데이터는 가상이며 실제 회사 정보를 넣지 않는다.
- 기본 결산월은 한국 시간 기준 지난달이다. 2026-10-01에는 2026-09를 선택한다. 사용자가 다른 월을 선택할 수 있다.
- PPT 5장의 부서별 진행률은 우선 부서 필터를 선택하면 해당 부서 진행률을 보여주는 방식으로 구현한다. PPT 6장의 전체 진행률은 부서 전체 선택 시 표시한다. 여러 부서의 진행률 막대 비교는 추가 후보다.

## 4. 데이터와 계산 규칙

| 필드 | 형식·예시 | 규칙 |
| --- | --- | --- |
| id | 자동 생성 고유값 | 필수, 변경은 id 기준 |
| 결산월 | YYYY-MM, 2026-09 | 필수 |
| 자료명 | 미지급 내역 | 필수, 앞뒤 공백 제거 |
| 담당 부서 | 구매팀 | 지정 목록 선택, 필수 |
| 제출 기한 | YYYY-MM-DD, 2026-10-05 | 유효한 날짜, 필수 |
| 요청 메모 | 거래처별 정리 | 선택 |
| 상태 | 미제출 / 제출 완료 | 최초 미제출 |
| 제출자 | 김OO | 제출 확정 시 필수, 앞뒤 공백 제거 |
| 제출 메모 | ERP 첨부 완료 | 선택 |
| 제출 일시 | 저장소·서버에서 자동 기록 | 제출 확정 시 기록 |

**입력·상태 규칙**

- 공백만 있는 자료명·제출자는 저장하지 않는다. 결산월·기한 형식과 부서 목록도 검증한다. 과거 기한은 지연 항목 등록·테스트를 위해 허용한다.
- 최초 등록 시 제출자·제출 메모·제출 일시는 비어 있다. 같은 자료명도 별도 요청으로 등록할 수 있다.
- 제출 입력 창의 [취소]는 아무 데이터도 변경하지 않는다. [제출 확정]은 상태·제출자·메모·일시를 한 번의 저장 작업으로 함께 변경한다.
- 완료 행의 [제출 취소]는 상태를 미제출로 되돌리고 제출자·제출 메모·제출 일시를 초기화한다. 다시 제출하면 새 정보를 기록한다.
- 여러 PC가 같은 행을 변경하면 마지막으로 저장에 성공한 변경을 적용한다. 다른 PC는 새로고침으로 최종 상태를 확인한다.

**계산값은 저장하지 않고 화면에서 계산한다.**

- 날짜 기준: Asia/Seoul. 제출 기한은 날짜만 저장한다. 제출 일시는 UTC 시각으로 저장하고 한국 시간으로 표시한다.
- D-day = 제출 기한 날짜 − 한국 시간의 오늘 날짜, 정수 일수. 양수는 D-N, 0은 D-day, 음수는 N일 지연으로 표시한다.
- 지연: 미제출이고 D-day < 0. 기한 당일은 지연이 아니다.
- 색상: 미제출이고 D-day < 0이면 빨강, 0~2이면 주황, 그 외 기본색. 완료 행에는 기한 경고색을 적용하지 않는다.
- 진행률: 현재 필터의 완료 건수 ÷ 현재 필터의 전체 건수 × 100, 소수점 버림. 10/16 = 62%. 전체 0건이면 0%.
- 제출·전체·지연 건수는 모두 현재 결산월·부서 필터가 적용된 목록 기준이다.

| F1 | 요청 등록·저장 | 결산월·자료명·부서·기한·메모 등록 | 새로고침 후 유지, 필수값·공백 오류 시 저장 안 됨 |
| F2 | 전체 현황 목록 | 선택 조건의 요청을 기한 빠른 순으로 표시 | A PC에서 등록한 항목이 B PC에서 새로고침 시 보임 |

| F5 | 필터·진행률 | 결산월·부서 선택과 요약 | 목록과 전체 건수 일치, 완료 건수와 버림 공식 일치, 0건이면 0% |

## 6. 화면과 공통 동작

README의 요청 등록 화면·제출 체크 화면·공용 현황판은 각각 요청 폼·제출 입력 창·목록과 요약 영역으로 제공한다. 별도 페이지 분리는 요구하지 않는다. 한 페이지에서 진행률 → 필터 → 목록 → 요청 등록 순으로 배치한다.

1. 상단: 결산체크, 진행률, 제출 n / 전체 m, 지연 건수. 예: 62%, 제출 10 / 전체 16.
2. 필터: 결산월(기본 지난달, 전체 월 선택 가능), 부서(기본 전체).
3. 목록: 결산월·부서·자료명·기한·D-day·상태·제출자·요청 메모·제출 메모·버튼. 미제출 행은 [제출 완료], 완료 행은 초록 상태와 [제출 취소].
4. 요청 등록: 결산월(기본 지난달)·자료명·부서·기한·요청 메모와 [등록].

- 최초 조회 중 로딩 표시. 0건이면 “등록된 요청이 없습니다”. 조회 실패는 빈 목록으로 처리하지 않고 오류와 [다시 불러오기]를 표시한다.
- 저장 중 해당 버튼 비활성화로 중복 클릭을 막는다. 저장 성공 직후 현재 화면의 목록·상태·진행률·건수를 별도 새로고침 없이 갱신하고, 실패 시 입력 유지와 오류·재시도 안내. 실패를 성공으로 표시하지 않는다.
- 등록 항목이 현재 필터에서 숨겨지면 저장 성공과 필터 변경 안내를 표시한다.
- 다른 PC의 변경은 새로고침 시 반영한다. 자동 갱신은 추가 후보다.
- 휴대폰에서는 표를 가로 스크롤할 수 있고 폼·제출 창·버튼을 사용할 수 있어야 한다.

## 7. 기술 방식과 제작 순서

localStorage는 PC 간 공용 저장소로 사용할 수 없다. 제작 전 저장·배포 방식을 검증하고 선택한다.

| 후보 | 선택 조건 | 준비 사항 |
| --- | --- | --- |
| A. Claude 아티팩트 + 공용 저장 기능 | 제작 계정에서 기능 제공 여부와 공유 주소의 PC 간 읽기·쓰기를 검증한 경우 | 제공 여부·접근 조건은 아직 미확인 |
| B. HTML + Supabase(DB) + Vercel(주소) | A 검증 실패 시 대안으로 검토 | 계정·DB 접근 정책·배포 설정 필요, 준비 시간은 환경에 따라 달라짐 |

기술 후보는 제공 가능성을 확정한 것이 아니다. 사용 환경에서 확인한 결과로 선택한다. DB 관리용 비밀 키는 브라우저 코드에 넣지 않는다.

**제작 순서**

1. 저장 방식·부서 목록 확정. A PC 저장 → 공유 주소를 연 B PC 조회·수정 → A PC 새로고침 반영을 확인한다. A 실패 시 B를 검토한다.
2. F1 제작·검증.
3. F2 제작 후 테스트 담당이 다른 PC에서 확인. 공용 저장·조회 중간 점검 통과.
4. F3 → F4 → F5 모두 제작·검증. F5 추가 후 제출 완료·취소에 따른 상태와 진행률의 즉시 갱신을 통합 확인한다.
5. 가상 데이터 15~20건 입력. 지연 2건, 임박 2건 포함. 날짜는 시연일 기준으로 준비한다.
6. 최종 배포 주소에서 9장의 완료 조건과 README의 시연 순서를 검증한다. 서비스 주소·저장소 주소·검증 결과는 이 PRD에 기록하며 README는 수정하지 않는다.

## 8. 테스트·한계·2일차 후보

- [ ] F3 제출 취소 후 상태·제출 정보 초기화, 새로고침 후 유지.
